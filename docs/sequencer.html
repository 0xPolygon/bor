Low-Latency Transaction Sequencing — Preconfirmations for Polygon PoS

Draft
Component: Bor (execution client)  ·  Author: Jerry (fchen@polygon.technology)  ·  Date: 2026-06-24
Store wire-format and APIs are specified in §10 below.

TL;DR. Today a transaction waits ~1.5–3 s to be included, and an RPC node waits a further ~500–1000 ms for the block to build and propagate before it can return a receipt. This proposal has the block producer publish each transaction to a centralized sequence store the moment it commits that transaction to the block it is building. RPC nodes stream that sequence, re-execute it, and return a preconfirmation receipt before the block is sealed — deterministic (the receipt is exactly what the block seals, §7) and requiring no consensus fork, only a producer-side scheduling change (§6).

Polygon/Bor vocabulary used throughout (skip if you already know it):

  • Heimdall — Polygon PoS’s consensus client; it selects validators and tells Bor who produces each block.
  • Span / sprint — validator-rotation windows. A span fixes the validator set; within it, block-production turns rotate each sprint (a fixed run of blocks).
  • VEBLOP — the producer-election model in which one validator is the active block producer at a time, with defined failover.
  • State-sync — L1→L2 messages the protocol injects into Bor at sprint starts; not user transactions.
  • Milestone — Heimdall’s periodic finality checkpoint for Bor blocks; once milestoned, blocks are final.
  • Rio, Indore — named Bor hardforks; the one fact that matters is given at each mention.

§1Problem

On Polygon PoS, a user typically waits ~1.5–3 seconds for a transaction to be included in a block. The block producer snapshots the executable set from its mempool once per block-production cycle, so a transaction arriving just after a snapshot waits almost a full cycle before it is even considered. On top of that, an RPC node today cannot return a receipt until the producer has built and propagated the block (~500–1000 ms) and the node has imported it. Both waits sit on the critical path of perceived confirmation latency and block sub-second user experiences.

Note: block time is configurable per network and has moved below 1.5 s on some deployments (Rio --miner.blocktime); the latency problem and this design are independent of the exact cadence.

§2Goals & non-goals

Goals

  • Return a transaction preconfirmation (an execution receipt) before the block is sealed, taking the ~500–1000 ms build/propagate/import step off the confirmation critical path.
  • Make every preconfirmation deterministic — the receipt an RPC node returns is exactly what the sealed block produces (§7).
  • Add this with no consensus fork — publishing and the store are an additive sidecar on the block producer’s build loop, and the one production-side change (the producer executes ahead of the announcement cadence to preconfirm on commit, §6) reuses Bor’s existing early-announcement rules, so peers validate blocks exactly as today.

Non-goals (v1)

  • Decentralized sequencing. A decentralized sequencer needs an additional consensus mechanism and adds latency; out of scope for now. The current block producer sequences — it already orders and executes as it builds.
  • Sequencing state-sync transactions. State-sync (L1→L2) is consensus-injected at sprint boundaries; it is not published. RPC nodes apply it from their own Heimdall like any Bor node, deterministically (§7).
  • Light-traffic inclusion latency. The mempool snapshot cadence (§1) is unchanged: in light traffic a transaction still waits for the next refresh before it is committed at all. Execute-ahead improves the inclusion side only under bursts (§6); the win this design ships everywhere is the confirmation leg — the receipt arrives before build/propagate/import instead of after.

§4Definitions

  • Transaction sequencing — the order in which the block producer commits transactions to a block, and the block boundaries between them, published as the BP builds.
  • Anchor — an RPC node’s latest imported block; the state all pre-execution starts from.
  • Confirmation (preconfirmation, or “preconf”) — the execution receipt an RPC node returns for a sequenced-but-not-yet-sealed transaction, by re-executing the published sequence.
  • Deterministic confirmation — a preconfirmation whose receipt is exactly what the block seals. In this design every preconf is deterministic; the only caveat is an ordinary chain reorg (§8).
  • Commit interrupt — the normal block-time cutoff: a transaction the BP has not committed when the block closes simply rolls to the next block (and is sequenced there when it executes).

Why the producer is the sequencer

The ordering decision is the BP’s execution order: it pulls the mempool, executes transactions in priority order, and commits them to the block. A separate sequencer would have to execute too — to know gas, state, and validity — so it would duplicate the miner rather than replace it. The producer is the sequencer by construction. Keep the store and any order-flow ingress as separate, independently-scalable services (so roadmap items like reserved block space, private order flow, and external preconf providers don’t require re-architecting), but the ordering itself stays in the producer.

Safety invariant

The BP publishes a transaction only after it has committed that transaction to the block it is building, and the published prefix is binding on the producer itself: Bor’s miner can internally restart the open block (resubmit and timeout interrupts, miner/worker.go), and a rebuild on the same parent must re-commit the already-published transactions in their published order before adding anything new; a rebuild on a changed parent (a reorg arrived mid-block) instead re-opens the block with a supersession open record (§8, §10). So the published sequence is always a prefix of what the BP will seal — publish and seal cannot silently diverge. The store is a best-effort publication channel; the sealed chain is the source of truth. Every failure mode below is analyzed against this invariant.

Sequence store

An append-only, replicated log of producer-published entries, mirroring each block’s lifecycle: a block-open record fixing the block’s header context, transaction records (ordered raw transactions), and a block-seal record carrying the sealed header — each chained to the prefix it extends over an authenticated write path (§10). It durably acks each entry before the preconf is considered valid (§3). Besides shielding the BP from read load and DoS, it is the hand-off channel on producer rotation: a newly-elected producer reads the tail to continue rather than starting fresh. It is not on the chain’s critical path — but it still needs its own HA, failover, and upgrade process, since preconfirmations stop (degrading to baseline latency) whenever it is down. The wire format, navigation (by block + tx hash), and APIs are specified in §10.

Authentication & trust. Entries carry no producer signature — the write path is protected by channel authentication instead: the BP publishes over an authenticated connection (mutual TLS with a per-validator credential — an operational secret, rotatable, and distinct from the validator’s consensus key). The store checks nothing against Heimdall: write access is the credential — which credentials exist and are active is operational (issuance and revocation) — and among authenticated writers the head check arbitrates (§10): exactly one chain, first-to-extend wins. A stale-but-credentialed producer can contend for the head — a nuisance resolved by revoking its credential, not a fork — and anything it lands is voided by canonical within about a block (§8). Keeping the consensus key out of the sidecar removes the cross-protocol signature surface entirely (nothing the sidecar emits can be confused with a header) and takes per-entry signing and per-entry ecrecover off the hot path. The flip side is a trust-model statement consumers must know: pre-seal content is store-attested — RPC nodes rely on the store’s authentication for who published the open block’s entries. The exposure is one block and self-healing: every seal record is self-authenticating (its header embeds the consensus seal, which normal canonical import verifies independently), and the sealed header’s roots commit to exactly the transactions and context published — so canonical voids anything mis-attributed within about a block (§8). Consumers add no attribution check of their own: they trust the authenticated store for pre-seal content, full stop. Producers are not declared in requests — identity is the channel, nothing more. The head check is the first line of defense for the partition / double-writing cases in §8.

Transport. RPC nodes consume as a stream (for latency) with a pull/replay fallback. Streaming’s reliability concerns — delivery, reconnection, gap detection, backpressure — are specified in §10 and tracked in §11.

Access (tiered). v1 exposes the store to our own RPC nodes, so preconf reaches clients of our RPC. Early/premium access can be granted to large, latency-sensitive customers; external RPC providers can later point their nodes at the store endpoint. A premium tier that pushes order flow to, and returns receipts directly from, the BP (collapsing both gossip legs) is a future PoC — gated on measuring the actual latency win and a product decision on pricing.

RPC nodes

Given the sequence endpoint, an RPC node re-executes the published transactions and produces preconfirmation receipts. It anchors at its latest sealed block and applies the committed records as they arrive. Confirmations are served through:

  • eth_getTransactionReceipt / eth_getTransactionByHash — the preconfirmation receipt (served with a preconf marker and a null blockHash until the block’s seal record supplies the hash; exact client-facing shape is an open item, §11).
  • the pending block tag on eth_call, eth_estimateGas, eth_getBlockByNumber, eth_getBalance, eth_getTransactionCount, eth_getCode, eth_getStorageAt — reflecting the preconfirmed (sequence-head) state.

Consistency check. A preconfirmation is only correct if the RPC node executed the right transactions, in order, on a contiguous chain head. Before issuing a receipt it verifies that the entry’s prefix_commitment matches the running head it has computed over the entries verified so far (every well-formed entry folds into the head whether or not it ends up applied — the chain-vs-apply rule, §10). Because the store is append-only, a mismatch means a gap — stop and catch up; the commitment chain never points backward. (A canonical-chain reorg of already-sealed blocks is handled separately by normal import: the node re-anchors its local pre-execution to the new sealed head, §8.) A stale or out-of-sync node returning confident-but-wrong receipts is exactly the risk this closes.

The RPC node executes against the block’s actual header (fixed at block-open) and its sealed parent, so it never guesses the context — which is what makes the receipt match the sealed block (§7).

§6Sequencing & block production

The block producer selects and orders transactions exactly as it does today — it pulls executable transactions from the mempool and executes them, in priority order, into the block it is currently building. Two things are new. First, as each transaction commits to the block, the BP publishes it to the sequence store as a record (§10); publishing is asynchronous and off the build critical path, so the BP never waits on the store to keep mining. Second, when the mempool is backlogged the producer executes ahead of the announcement cadence rather than pacing to it — described at the end of this section.

  • Ordering is the BP’s normal build order (priority fee, etc.) — there is no separate sequencing cadence; a transaction is published the moment it is committed.
  • Block boundaries are the BP’s normal block boundaries, and each boundary is published: sealing block N emits a block-seal record (N’s sealed header — fixing N’s hash), and opening block N+1 emits a block-open record (N+1’s header context: number, timestamp, parent hash, gas limit, base fee) before its first transaction (§10). Since N+1 opens only after N is locally sealed (sealing can run ahead of announcement — below), consumers always know N+1’s parent and exact header, even before N is announced (§7).
  • Commit interrupt is just the block-time cutoff: a transaction the BP hasn’t committed when the block closes rolls to the next block and is published there when it executes. Because a transaction is published only after it commits, a published transaction is always exactly in the block it executed into — nothing slides.
  • Fees are standard: the BP has executed the transaction, so it charges actual gas under normal EIP-1559 — no special gas accounting.

A preconfirmation is issued once the store durably acks the published record (§3). Cancellation is therefore possible until the BP includes the transaction — ordinary mempool replacement, with no artificial cadence window.

Execution runs ahead of announcement

One producer-side change lets a burst of demand be preconfirmed early. In normal traffic the producer pulls the executable set from its mempool when it builds and on Bor’s existing recommit/refresh cycle (the §1 snapshot behavior — unchanged here), and executes what is there; when the mempool is light it idles between refreshes until the block’s scheduled time — fine. The change matters under a burst: when a spike floods the mempool there is always more to execute, so the producer does not idle — it keeps executing and can fill a block to its gas limit and seal it before that block’s announcement time. Rather than idling (nothing to gain) or broadcasting immediately (peers reject a block announced before its parent’s timestamp has passed), it holds the sealed block, releases it on cadence, and immediately opens the next one — so its execution pipeline runs ahead of the announcement schedule and drains the burst faster.

This is a scheduling change, not a consensus one: it reuses Bor’s existing early block announcement rules (PIP-66; the relaxed verifyHeader timing already live on mainnet and Amoy, consensus/bor/bor.go). Post-Giugliano a peer accepts an announced block once now ≥ parent.Time, with header.Time at most 30 s ahead of its clock (maxAllowedFutureBlockTimeSeconds). Two consequences. First, the announcement schedule is unchanged: the producer releases each held block at the same wall-clock point it would have announced it had it been sealed just-in-time, so the network sees today’s cadence and backup-producer succession is unaffected — the Giugliano rule’s role is to guarantee a long-held block is exactly as valid at that point (and it would even permit releasing up to one slot early, once now ≥ parent.Time, if the import head-start is ever wanted). Second, those peer rules bound announcement timing, not how far execution may run ahead — a held block passes validation whenever its slot arrives, regardless of when it was sealed. The buffer is therefore bounded by an explicit producer-side seal-ahead cap (a config limit on sealed-but-unannounced blocks; value to be chosen, §11) that caps preconf exposure to producer failure and keeps header timestamps meaningful.

Buffering model. A held block is sealed and buffered without being imported into the producer’s own chain: importing it would advertise it (head / total difficulty in the eth handshake) and serve it to peers ahead of schedule — and a peer pulling a block two-plus slots ahead would reject it as a future block. Instead the miner keeps building on the buffered block’s post-state (not the imported chain head — a worker change, §11), and import + broadcast happen together when the slot arrives. Held blocks are never advertised or served to peers before release.

The effect is to decouple execution from announcement: transactions are committed, sequenced, and preconfirmed continuously, ahead of the announcement slot, so preconfirmation latency tracks execution rather than the block cadence (§9). RPC nodes keep pace by replaying the published sequence — each block’s open record hands them its exact header context and its seal record the resulting hash (§10) — so they pre-execute past the last announced block and, when a held block is finally announced, import it and match by construction (§7). A held block is also never hostage to its producer: its seal record plus its transaction records are the complete block (sealed header + body), so if the producer dies anyone can reconstruct it. Whether a successor may announce it as-is depends on VEBLOP failover semantics — if the failover election re-cuts producer assignments from the canonical tip, the dead producer’s signature is no longer authorized for those heights (§11); even then the successor replays the held transactions under the pinned open context, so the preconfirmed receipts survive producer failure either way (§8).

Because the BP executes each transaction before publishing it, there is no pre-execution guess to get wrong: the RPC node runs the same transactions the producer already ran, on the same state, with the same header. Reverts are deterministic too — a reverting transaction is published with its status = 0 receipt.

State-sync

State-sync transactions are consensus-injected at sprint starts and are not published — an RPC node is itself a Bor node and applies them from its own Heimdall during execution, exactly as in normal import. A block’s set is the Heimdall events up to header.Time − StateSyncConfirmationDelay (CommitStates, consensus/bor/bor.go) — 128 s on mainnet since Indore. Because a block is sequenced only as it is built, that cutoff sits comfortably in the past, so every node applies the same set and the result is deterministic. One interaction with execute-ahead (§6): a block sealed D slots ahead has header.Time up to D × blocktime past the wall clock, shrinking the cutoff margin to 128 s − D × blocktime — an explicit input to the seal-ahead cap choice (§11). And because a replayed block pins the superseded timestamp (§8), its state-sync cutoff — hence its event set — is unchanged too. (As for any Bor node, this assumes a healthy local Heimdall.)

The only residual: reorgs

The RPC node never guesses, so the only thing that can make a preconf wrong is the sealed chain itself changing — an ordinary pre-finality reorg, bounded by Bor’s milestone finality. The common case is a producer change on the same parent, and here the preconfirmation holds where it matters: the replacement producer follows the same sequence store — it replays the identical transactions in the identical order under the superseded block’s pinned context (same timestamp, gas limit, and base fee; §8) — so each one keeps its position and receipt. Under VEBLOP even the difficulty is identical (always 1 — a single-producer set makes Difficulty() constant, §7 table), so no header field a transaction can read changes. What changes is the block hash alone — a different validator signs the block, so the seal in extraData hashes the header to a different value even though everything a transaction can observe is unchanged. (In a multi-block replay there is one carve-out: reads of a replayed ancestor’s hash — BLOCKHASH / the EIP-2935 history contract — see the replacement hashes, §8.) The rarer case — a reorg that actually changes a block’s parent state — does change results, and those preconfs are voided and re-issued against canonical (§8).

§8Failure scenarios

Preconfirmations need an explicit consistency model, because the store is centralized while the canonical chain is not. The model: the sealed canonical chain is always the source of truth; the store is an append-only, best-effort publication channel, and consumers reconcile their own view against the sealed chain. The BP honors the safety invariant (it seals what it committed), so in the normal case store and chain agree. When they can’t — the rare cases below — the chain wins and affected preconfirmations are voided. The right framing for users is an SLA on deterministic preconfirmation (a quantified probability), not a hard guarantee.

Reconciliation (canonical wins)

When the published sequence and the sealed chain diverge, the store is not rewound — it is append-only. Reconciliation happens at the consumer: an RPC node pre-executing the published sequence sees that the sealed chain doesn’t match the suffix it executed, so it voids the preconfirmations from that suffix and re-anchors its local pre-execution to the sealed head — canonical is always the source of truth. The orphaned published records are superseded in place, never deleted, and the commitment chain only ever grows; re-anchoring the node’s own speculative state is not a sequence rewind. This consumer-side path is what makes every scenario below recoverable.

Reorg (replay vs. reconcile)

A pre-finality reorg replaces a sealed block. Two sub-cases. (1) A producer change on the same parent — the common case: the newly-elected producer reads the store tail and replays the same transactions, in the same order, on the same parent state, because it follows the store rather than re-selecting from its own mempool. Its replay pins the superseded block’s open context — same timestamp, gas limit, and base fee — and under VEBLOP the difficulty carries over by itself: a single-producer set makes Difficulty() equal 1 for every producer (§7), so nothing in the header context is producer-dependent. Pinning is consensus-legal: both timestamp rules are lower bounds — parent.Time + period ≤ header.Time in header verification, and header.Time ≥ parent.Time + CalcProducerDelay(number, succession) in seal verification (IsBlockEarly, consensus/bor/bor.go) — and both bind identically for the replayer (same number, and the same succession 0 in VEBLOP’s single-producer set), so the superseded value satisfies them on the same parent; the gas-limit and base-fee bounds are likewise checked against that same parent, which the superseded values already passed. (Bor’s own miner would recompute the timestamp on a rebuild — the replay path overrides that producer-side policy.) So every transaction keeps its position and its exact receipt — same timestamp, gas limit, base fee, and state-sync set. What differs is the block hash alone, because a different validator signs the replacement block (a new seal in extraData). In the store, the replacement is a supersession (§10): the new producer appends a block-open record for the same height naming the same parent, republishes the transactions, and seals — the chain never rewinds, and consumers void and re-issue only what actually changed. (2) A reorg that changes a block’s parent state genuinely changes transaction results; no replay can match the old receipts, so consumers void the affected preconfs and re-issue them against canonical (as in Reconciliation above). Either way the store stays append-only; milestone finality bounds how far a reorg can reach.

Store failure modes

  • Hard down / unreachable. The BP keeps mining (invariant holds); preconfirmations pause and latency degrades to baseline. Already-issued preconfirmations stay valid because the BP still seals what it committed (and when publishing resumes, the forward-jump reconcile confirms rather than voids them, §10).
  • Slow / unresponsive but up. RPC nodes treat a slow store like an unavailable one — fall back to baseline past a freshness bound rather than serve stale data.
  • Stale reads. Caught by the §5 consistency check (the commitment chain vs. the node’s head); a behind node catches up before emitting receipts.
  • Internal inconsistency / partial writes. Entries are atomic, with the commitment chain making gaps and corruption detectable; durability/replication is specified in §10.
  • Compromised / malicious store. Pre-seal content is store-attested (§5), so a compromised store or egress could fabricate an open block’s stream; consumers speculatively execute it until the block’s seal record — which cannot be forged (self-authenticating consensus seal) — or the canonical announcement contradicts it, voiding the affected preconfs. Exposure is bounded to roughly one open block per attempt and burns the operator’s accountability; egress TLS + auth and the §10 audit trail are the mitigations.

Producer hand-off (span rotation / VEBLOP election)

The producer changes at span rotation and per the VEBLOP producer-election rules — one producer per block, so this is a clean hand-off, not an in-span backup takeover. The newly-elected producer reads the store tail and continues from the committed sequence before sequencing anything new. Sealed-but-unannounced blocks in the tail are complete blocks (§6): if VEBLOP failover leaves their heights assigned to the dead producer, the successor announces them as-is; if the election re-cuts from the canonical tip (making the old signature unauthorized at those heights), the successor instead replays their transactions under the pinned context and supersedes (§10) — receipts hold, only the hashes change (one carve-out: BLOCKHASH / history-contract reads of a block inside the replayed window see the replacement hashes, §7). Which of the two VEBLOP prescribes is pinned in §11, along with whether superseded per-height assignments stay queryable. Outcome: a brief latency bump during the transition, no inconsistency.

Deployment assumption (stated, not assumed silently): this hand-off behavior — replay the tail rather than rebuild from your own mempool — is publisher-sidecar logic, so it holds only when the successor runs the sidecar. Preconfirmations are offered only while the elected producer publishes: a successor without the sidecar produces valid blocks but publishes nothing — preconfs pause to baseline for its tenure, and any sealed-but-unannounced predecessors it ignores are orphaned (their preconfs void via reconciliation). The rollout therefore targets every producer-set candidate (today’s BPs are Polygon-operated; the VEBLOP producer set is small), and the §11 SLA prices the non-publishing-successor case. When publishing resumes after a dark tenure, the next producer’s open record simply names its actual canonical parent — the supersession rule (§10) re-anchors the store past the unpublished stretch.

BP sequenced, then died

  • The producer fails after publishing some sequence; the span rotates / a new producer is elected.
  • Sealed blocks in the tail survive as receipts. A seal record plus its block’s transaction records are the complete block: announced as-is where failover semantics allow, otherwise replayed under pinned context and superseded (see Producer hand-off above) — either way the preconfirmed receipts hold (one carve-out: ancestor-hash reads within a replayed window, §7).
  • The open (unsealed) block is the loss window. Its published transactions have no seal; the successor replays them into its own block on the same parent under the pinned open context, so they keep position and receipt (the §7 ancestor-hash carve-out aside) under a supersession open record (§10).
  • If the successor can’t read the store (store also down) or doesn’t run the sidecar, it builds fresh; the orphaned published suffix is superseded by canonical and its preconfirmations are voided at consumers — lost. This is the core best-effort window the SLA must price, and the case the future all-producer order-ack (§3) would close (the acked ordering would already be held by every producer).

Equivocation & partition (two producers writing at once)

Two cases can produce conflicting sequences for the same height: a stale producer still writing after a rotation/partition, and the same validator credential running on two nodes (which authentication alone can’t disambiguate). Both are prevented at the store — rather than detected after the fact — by a simple head check: a record is accepted only if it extends the current head of the chain.

Each record carries a prefix_commitment — the chain head just before it; appending a block-open record advances that head by folding in the block’s header context, a transaction record by folding in its transactions, and a block-seal record by folding in the sealed hash to close the block (the per-block construction is in §10). The store appends a record only if its prefix_commitment equals the store’s current head; otherwise it rejects the record, and the producer must catch up (re-read the published tail) before publishing again. So two writers contend for the same head: the first wins and advances it, the second is rejected and catches up. The store therefore holds exactly one chain — neither a stale producer nor a duplicate-key node can fork it. And because a preconf is issued only after the store durably acknowledges a record (§3), a rejected record (never acknowledged) can’t break an issued preconf.

This requires the head check to run on a single write path (the store ingress); if that write path can’t reach a majority of the store’s replicas it can’t acknowledge a record, so the store can’t split into two disagreeing copies either. The store’s single chain remains subordinate to the sealed canonical chain: if the producer whose record was accepted somehow loses canonical consensus, consumers reconcile against canonical (voiding the affected preconfs) while the store stays append-only. Reconcile producer-election edge cases with the VEBLOP spec.

§9Latency budget

A preconfirmation is available as soon as the block producer commits the transaction, plus a small constant: publish + the store’s durable (replicated) ack + stream + RPC re-execute — tens of milliseconds end-to-end, dominated by the durable ack. The headline win is what it removes — the ~500–1000 ms to build, propagate, and import the sealed block — so the RPC node returns a receipt before the block is sealed rather than after.

Because a transaction is published only after the BP executes it, the preconf trails the BP’s execution by that small constant and can never precede it — the RPC node is continuously a publish-round-trip behind the producer, not a block behind. There is no cadence wait: the BP publishes each transaction the moment it commits — and because the producer can run its execution ahead of the announcement schedule when demand is bursty (§6), commit (and therefore preconfirmation) is not paced by the block time; under a burst a transaction can be preconfirmed well before the block that will contain it is announced.

One stated assumption behind that figure: the consumer keeps pace. An RPC node must re-execute the stream at least as fast as the producer builds it (with headroom — it is serving reads at the same time), or the lag compounds for the burst’s duration: preconf lag is max(publish round-trip, execution deficit). A sustained deficit degrades to the §8 freshness-bound fallback (baseline latency) rather than ever serving stale receipts.

Under a burst the producer never idles — it executes at full speed, publishing each transaction to the sequence store as it commits, and seals blocks ahead of their announcement slot. RPC nodes stream the sequence and re-execute, so the receipt is ready tens of milliseconds behind execution, while the block is announced later on the consensus cadence (§6).

Event sequence

The end-to-end event sequence for one record — from sequencing to a preconfirmation receipt:

Data model

The sequence carries three kinds of entry, mirroring a block’s lifecycle. A block-open record fixes the block’s header context (number, timestamp, parent hash, gas limit, base fee) the moment the producer opens it — every header field execution depends on (§7). Transaction records carry one or more sequenced transactions for that block (never spanning two blocks). A block-seal record, appended the moment the block is sealed, carries its full sealed header — closing the block and handing consumers the one thing they cannot recompute: the sealed hash (§7). Together a block’s seal record and its transaction records are the complete block (header + body), reconstructible and announceable by anyone (§8).

Publishers send bare entries; consumers receive each entry exactly as published — there is no store-added wrapper or metadata. Pre-seal attribution rests entirely on trusting the store’s authenticated ingress (§5).

The tx_i folded into the commitment are the raw signed transactions; the fold’s field serialization is a fixed canonical(…) encoding — deferred, but it must be byte-identical across clients for commitment parity. The per-item fold’s domain-separation tags (one per entry class) are normative. Entries themselves carry no producer signature (§5): the write path is channel-authenticated, and the only producer-signed artifact in the system is the one the protocol already has — the consensus seal inside each seal record’s header.

The commitment chain is a running hash over the sequence, advanced by a per-item fold: head′ = keccak256(head ‖ tag ‖ item), where an item is an open record’s context fields, one transaction, or a sealed hash, and tag is the item’s entry-class domain tag (one per entry class, so no folded item can collide across types). Folding per transaction — not per record — is normative: it makes the chain independent of how transactions are batched into records, and the two natural readings (iterated fold vs. one flat hash over a block) produce different bytes, so only the fold is correct. Named points: C_open(N) is the head after folding N’s open context into the previous head; after the block’s first k transactions the head has folded tx_1 … tx_k one at a time, reaching C_block(N) once all are in; the seal record folds the sealed hash, giving C_seal(N) = keccak256(C_block(N) ‖ tag_seal ‖ sealed_hash(N)) — the per-class tag participates at every named point. On the normal path the next open record chains from C_seal(N) with parent_hash = sealed_hash(N). Because an open record must name its parent’s sealed hash — which exists only once that parent’s seal record does — “a block is sequenced only after its parent is sealed” is a structural property of the chain, not a timing convention. The chain’s genesis seed is pinned too: head_0 = keccak256(domain ‖ chain_id ‖ format_version), so a stream can never be replayed across networks or format revisions — it fails structurally, not by convention. (That protection covers consumers that computed the chain from the seed; a cold-start consumer adopts the stream’s prefix as its seed instead, so its network/format binding comes from parent_hash-against-canonical and seal verification.) And since every head folds the one before it, any change anywhere in history changes every head after it. The chain serves two jobs: store↔sequencer agreement (the head check below) and consumer gap/order detection.

Supersession (chain repair). The happy path opens each block with parent_hash equal to the previous seal record’s hash. Any open record whose parent_hash is not the current tip is a re-anchor — the trigger is the parent, not the height. Three shapes, covering the repair cases of §5/§8: a replacement block at a height the store already sealed (backward), a mid-block parent change — re-opening the still-open height on a new parent when a reorg arrives mid-build (the §5 rebuild case) — and a producer resuming after a tenure that never published (a forward jump whose parent is a canonical block the store never saw). Every re-anchor still chains from the current head — the store remains one append-only chain and the head check is unchanged — while parent_hash names the sealed block it actually builds on. The store validates what it can — writer authentication, the head check, and — whenever the named parent is store-known — that the open’s block_number is that parent’s height + 1 — but it is not a chain validator: consumers verify parent_hash against seal records or their canonical chain. A re-anchor that replays a superseded block pins that block’s open context (§8). Consumers treat every entry above the named parent as superseded: void those preconfs and re-apply from the new open — the consumer-side reconciliation of §8, made concrete. Superseded entries are never deleted and the chain only grows.

Self-supersession is auditable. Nothing above stops the currently elected producer from re-anchoring to rewrite what it already published — every check would pass. To keep §3’s “final once published” honest and measurable, the audit is chain-wide and justification-aware. On any same-producer re-anchor the store compares the whole superseded suffix against the replacement generations and records every published transaction dropped or reordered anywhere in it — so the two-step dodge (re-anchor the parent intact, rebuild the child without the victim transaction) is caught exactly like a direct drop. What a record means depends on the re-anchor’s justification: onto the same parent there is no reorg to explain it, so a same-producer re-anchor of an already-sealed height — or any drop or reorder — is flagged as a producer revocation; onto a new canonical parent it is a chain-level reorg revocation, priced as such in §8, and transactions that became genuinely un-replayable on the changed parent are expected drops, not misbehavior (a reorg below held blocks legitimately forces the still-elected producer to re-anchor its own sealed heights, §6). A successor’s re-anchor onto the same (height, parent) carries the same preserve-the-prefix obligation (§8 requires a replaying successor to keep it; pinned context leaves no legitimate reason to drop it). Flagged supersessions are the revocation evidence — store-attested superseded records, plus the consensus-signed headers of any sealed generation — and the rate is an SLA metric (§8).

Binding the full open context and, through the seal record, the sealed hash means the chain commits to the complete determined block and its identity — every header field execution depends on, not just the transaction list. Coinbase is the one header input without a field: it follows the producer/fork rules (§7).

Because a transaction is published only after the BP commits it to a block, its block assignment is canonical — the store’s block boundaries (open → transactions → seal) match the sealed chain’s. The structural invariant the store enforces is the commitment chain (the head check below); the sealed chain remains authoritative under a reorg (§8).

Deliberately absent:

  • No cursor / offset / sequence number — the backend’s internal positions are never exposed; the resume token is the consumer’s own commitment head, protocol state both sides already compute.
  • No positional duplicates. Transaction records carry no block number or timestamp, transactions no index, and the seal no height: the head check makes stream position authoritative — a record’s block is whatever the last open record opened, a transaction’s index is its count from that open (the per-transaction fold makes batching irrelevant), and the seal’s height is inside its header. A duplicated field could only agree (dead weight) or disagree (a bug with two answers); the open record states each block’s context exactly once.
  • No per-tx attestation. A producer-signed, wallet-portable placement proof was considered and dropped with producer signing (§5): it would be the sidecar’s only validator-key use. Accountability rests on the self-authenticating seals and the §10 audit trail; if a portable proof is ever needed it returns as an opt-in extension with its own domain tag.
  • No void / rewind record — the chain only grows; a divergence from canonical is reconciled at the consumer against the sealed chain, never by rewinding the store (§8).

A consumer is itself a Bor node, so its cold-start anchor is its own chain head (a block number), and its precise warm-resume point is its running commitment head — the store indexes each entry’s post-fold head, so after=head:… resumes at exactly the occurrence the consumer verified. This is why the head, not a transaction hash, is the resume token: supersession can leave several generations of entries at one height, making a tx hash ambiguous as a position (and resolving it “latest” would skip the re-anchor records a behind consumer still needs) — while every head value is unique to its position by construction. Gap and order come from the commitment chain, not an integer. The block-number anchor never expires: if a presented head has aged out of retention, the consumer re-anchors at a block number and adopts the seed as at cold start (see the per-entry check). The block-addressed forms resolve to the latest generation at that height (/v1/block/{n}, after=block:n); a transaction hash that appears in more than one generation likewise resolves to its latest position for application-level lookup.

Publisher API (producer → ingress, gRPC)

Internal, trusted, latency-sensitive. The producer never deals in positions: it chains each entry to the prefix with a commitment and resolves its right to write purely by holding a writer credential on an authenticated channel (§5). It needs no tail-fetch call of its own: on takeover or after a rejection it learns the current head exactly as any consumer does — by reading the stream to the tip via the consumer API (below) and re-applying the records it missed; its running head after the last record is what its next record must extend. Those records have to be re-applied anyway (to rebuild running nonces, balances, and block boundaries), so the head falls out for free.

gRPCPublish(Entry) → Ack { status } One entry — a BlockOpen, transaction Record, or BlockSeal (a oneof); accepted only if its prefix_commitment equals the store’s current head. Carried as a bidirectional stream: entries are pipelined, one ack per entry in the order received — a rejection doesn’t close the stream, but everything pipelined behind it fails the head check too, so the producer stops, resyncs, and resumes.

The head check. The ingress holds the chain’s current head and accepts a record only if its prefix_commitment equals it. On a match it appends and advances the head — folding in an open record’s header context, a transaction record’s transactions, or a seal record’s sealed hash (per the commitment-chain construction above) — then acknowledges it; on a mismatch it returns STALE_COMMITMENT and the producer reads the tail via the consumer API, adopts the store’s head, and rebuilds before publishing again. Forcing concurrent writers onto one chain is what prevents the equivocation / partition forks; the threat model, and why a rejected record can’t break an issued preconf, are in §8.

Producer identity. Producers aren’t declared in requests — the ingress takes the writer’s identity from the authenticated channel (the per-validator credential, §5) and validates nothing else about it: the store is chain-blind, and contention between credentialed writers is settled by the head check alone. Which producers hold credentials tracks the VEBLOP election operationally, not in-protocol.

Consumer API (RPC node / external → egress gateway)

Untrusted-facing; every connection/request is authenticated (API key / JWT). Clients reach only the gateway, never the backend. The native surface is gRPC (a server-streaming Stream, a pull Range, and GetBlock — same message shapes as the publisher side); the gateway may additionally re-encode it as the HTTP + WebSocket forms below for external clients — identical fields and semantics, so the endpoints are documented once in HTTP notation.

WS/v1/stream?after={ head:<bytes32> | block:<n> } → entry frames (block opens + transaction records + block seals, exactly as published) + {"t":"live"} when caught up to tip + ping/pong
GET/v1/records?after={ head:<bytes32> | block:<n> }&limit=<n>&wait=<ms> → { entries: [Entry], next: "head:<bytes32>", live: bool }
GET/v1/block/{n} → block n’s entries — its BlockOpen, its transaction records, and its BlockSeal (with the sealed hash) once sealed; inclusive fetch

after (exclusive; same in both modes): head:<bytes32> resumes right after the entry whose post-fold head equals the value — the consumer presents its own running head, so the stream continues with exactly what it has not applied, including any re-anchor records; block:<n> resumes after block n’s latest generation (cold start: a fresh node passes its sealed chain head, then adopts the seed per the per-entry check); omitted = from the earliest retained entry; next is returned as head:<bytes32>, so paging is after = next. An aged-out or unknown head returns an error and the consumer falls back to the block anchor. There is intentionally no latest/live-only value — it would skip the entries between a consumer’s head and the tip.

limit caps records per response (a server default/max applies). wait is a long-poll budget: if fewer than limit records are ready, the request is held up to wait ms for more before returning — live:true means the response reached the tip.

Per-entry consumer check. (1) Attribution. Entries carry no producer signature and no attribution metadata: authorship pre-seal rests entirely on the store’s authenticated ingress, and the consumer trusts the store for it — §5’s trust model prices exactly this. Seal records remain independently checkable (the header embeds the consensus seal, verified by normal canonical import), and canonical voids anything mis-attributed within about a block (§8). (2) Chain everything, apply selectively. Fold every well-formed entry into the running head — the chain is transport integrity, and superseded or stale entries keep their place in it; whether an entry is applied is decided by rules (3)–(5). Each entry’s prefix_commitment must equal the running head — a mismatch means a gap (stop and refetch), since the append-only chain never points backward; at a cold start — or any block-anchored resume after its head aged out of retention — the consumer adopts the first entry’s prefix_commitment as its seed (it cannot recompute it from sealed state) and verifies forward — integrity from there comes from the chain and the self-authenticating seals. (3) For a block-open record: if parent_hash is the consumer’s current speculative tip (the sealed or open block it would extend), apply it — adopt the open context (timestamp, gas limit, base fee — difficulty is the constant 1, §7) as the new block’s header. Any other well-formed open is a re-anchor: verify parent_hash names a sealed block it holds (a seal record, or a canonical block), that the parent is not below the consumer’s own last milestone-finalized height (the mechanical counterpart of “canonical wins”, and the only finality guard in the system — the store knows nothing of Heimdall finality, so a re-anchor under finality is held and alerted by the consumer, never applied), and that block_number equals that parent’s height + 1; then void every applied entry above that parent — including a partially-applied open block — and re-apply from this open (§8). On a forward jump, reconcile before voiding: blocks in the superseded stretch that sealed canonically exactly as published are confirmed by import, not voided — only genuine divergence is (§8). If the named parent is not yet held (a forward jump can name a canonical block a lagging consumer hasn’t imported), fold the entry but defer application until the parent arrives via normal import — past the freshness bound, fall back to baseline (§8). (4) For a transaction record, apply transactions in order (fold but don’t apply if its block was superseded). (5) For a block-seal record, take sealed_hash = keccak256(header) as the just-closed block’s hash and cross-check the sealed header twice: its number, timestamp, parentHash, gas limit, and base fee must equal the applied open context (publish and seal may not silently diverge, §5), and its state root, receipts root, and gas used must match the consumer’s own re-execution. On a mismatch: void (or mark suspect) the block’s already-served preconfs, fall back to baseline latency, resume pre-execution only from the next canonical import, and raise an operator alert — this class is a determinism bug or bad Heimdall data, not a transient. (6) For state-sync, see §7. Receipts and pending-tag state are served by the RPC node, not the gateway.

Verification

Order and content integrity come from the commitment chain; authorship pre-seal comes from the authenticated write path (store-attested, §5) and is proven at each seal record, whose header embeds the consensus seal — verified independently by normal canonical import. No producer signing, no per-entry ecrecover. A standalone, wallet-verifiable placement proof is deliberately absent (see the data-model list): the seal record already gives every consumer a consensus-signed commitment to the block’s exact content one block later, and anything stronger would put the validator key back in the sidecar (§5).

Store requirements (backend deferred)

The backend is an internal choice for later; whatever realizes the store must provide:

  • A durable, replicated, totally-ordered, append-only log — records are retained (never rewritten) for a window comfortably past milestone finality and the slowest consumer’s recovery (minutes-scale), so every position stays reachable. Superseded and flagged generations are additionally archived durably beyond the streaming window (or exported as audit events) — they are the evidence behind the supersession audit and the §8 revocation-rate SLA.
  • Enforcement of the commitment chain (the head check) — order and integrity. block assignment is canonical (a transaction is published only after the producer commits it to a block); the sealed chain remains authoritative under a reorg (§8).
  • A single write path (the ingress): channel authentication + the head check, then append — and the head check must be atomic with the replicated append at the log layer (a conditional append: commit only if the head still equals the expected value, or equivalently fenced/leased leadership). An in-memory check in the ingress is not enough: during an ingress failover overlap, two instances could each read the same head and each durably append a different successor. If the write path can’t reach a majority of replicas it can’t acknowledge a record, so the store can’t split into two disagreeing copies (§8).
  • Read fan-out decoupled from consumer count (the egress gateway): the log is read once per gateway instance and fanned out in memory, so read load is O(gateway instances), not O(consumers); a recent-window buffer serves live reads and reconnect backfill, with read-through to the log for older positions within retention.
  • Internal positions never exposed. The backend’s positions are used only to seek/index (head → position, block → position range, tx_hash → latest position); the API navigates by commitment head + block number only.

§11Open questions

  1. Consensus impact. Confirm no fork is needed — publishing, the store, and RPC pre-execution are off-chain, and the producer-side execute-ahead / hold-until-announceable scheduling (§6) rides Bor’s existing early-announcement rules so peers validate blocks exactly as today. Verify the held-block scheduling stays within the verifyHeader future-block bound and does not perturb backup-producer succession (§6).
  2. Timestamp at block-open. Confirm the header timestamp is fixed when the BP opens the block (before the first tx executes) and is the value sealed, so preconf and sealed receipts agree (§7).
  3. Reorg handling. Specify the replay-vs-reconcile boundary: when a newly-elected producer replays the published sequence vs. when consumers void and re-issue against canonical (§8). In particular, pin the VEBLOP failover semantics for held blocks: does the failover election resume above the store tail (successor announces a dead producer’s sealed-but-unannounced blocks as-is) or re-cut from the canonical tip (successor must replay them under pinned context and supersede)? (§6, §8)
  4. Store consistency SLA. Quantify the best-effort loss window: the open (unsealed) block when a producer dies, sealed-but-unannounced blocks if no publishing successor announces them, a successor that doesn’t run the sidecar (§8), plus pre-finality reorgs — and decide whether the all-producer order-ack upgrade (§3) is worth building.
  5. Partition / equivocation. The head check (§8) forces concurrent writers into a single chain; the remaining work is confirming it runs on a single write path and reconciling producer-election edge cases with the VEBLOP spec.
  6. Streaming transport semantics. Delivery guarantees, reconnection, gap detection, backpressure for the store stream (spec’d in §10).
  7. Ordering policy. The order is the BP’s normal build order (priority fee); document the MEV implications.
  8. Access & premium tier. Pricing/packaging of preconf access (our RPC nodes → premium customers → external providers), and a PoC of the direct BP→RPC receipt path to measure its latency win (§5).
  9. Reserved block space. Needs its own spec: who reserves, how it’s configured/enforced, and what happens to unused reservation.
  10. Ingress authentication. Pick the writer-auth mechanism (mutual TLS with per-validator credentials, or a private-mesh equivalent), how the credential binds to the validator identity, and its issuance / rotation / revocation lifecycle. It replaces producer signatures on entries (§5), so a leaked credential means a fabricated pre-seal stream until the seals expose it (§8) — revocation speed matters.
  11. Client-facing RPC semantics. Pin the preconf receipt shape (null blockHash plus a preconf marker until the seal record supplies the hash — then populated pre-announcement?) and the pending-tag behavior when the node’s pre-execution runs several sealed-but-unannounced blocks ahead (§5).
  12. Producer integration. Verify the published-prefix binding across every miner restart path (commitInterruptNewHead / Resubmit / Timeout, miner/worker.go): same-parent rebuilds must replay the published prefix exactly; parent-change rebuilds supersede (§5, §10). Verify pinned-context replay overrides the miner’s own timestamp recomputation (the minBlockBuildTime bump is producer policy, not consensus) and passes both consensus lower bounds (the header timestamp rule and IsBlockEarly in seal verification) on every replay path (§8). Implement and verify the §6 buffering model: the worker builds on the buffered block’s post-state rather than the imported head, held blocks are never advertised (handshake head/TD) or served to peers before release, and the txpool tracks the buffered head during seal-ahead — pruning included transactions and evaluating executability against the buffered post-state, not the announced head — or selection re-offers already-included transactions and stalls the burst drain (§9). Bypass Prepare’s pacing sleep (the wait-until-parent-timestamp delay in consensus/bor/bor.go — producer policy, not consensus): opening on a held, future-timestamped parent otherwise blocks until that parent’s slot and stops execute-ahead outright. Choose the seal-ahead cap value — inputs: preconf exposure to producer failure, header-timestamp meaningfulness, and the state-sync cutoff margin 128 s − depth × blocktime (§6, §7).
